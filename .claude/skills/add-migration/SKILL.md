# Миграция схемы

Выкладка идёт без остановки: во время обновления старая и новая версии сервиса работают одновременно с одной базой. Поэтому миграция обязана быть совместима с предыдущей версией кода.

1. Определи владельца. Схема `engine` — миграции в `services/engine`. Схема `gateway` — миграции в `apps/gateway`. Чужую схему не трогай.
2. Разрешено в одном релизе:
   - новая таблица;
   - новая колонка с `NULL` или с `DEFAULT`;
   - новый индекс (`CREATE INDEX CONCURRENTLY` на таблице с данными);
   - новое ограничение как `NOT VALID` с последующим `VALIDATE`.
3. Запрещено в одном релизе: удаление колонки или таблицы, переименование, смена типа, `NOT NULL` на существующей колонке без значения по умолчанию.
4. Несовместимое изменение раскладывай на релизы:
   - релиз 1: добавить новое, код пишет в старое и новое;
   - релиз 2: перенести данные, код читает новое;
   - релиз 3: удалить старое.
5. Миграция только вперёд. Уже выложенную миграцию не редактируй, исправление — новая миграция.
6. Перенос данных на большой таблице делай пачками, не одним `UPDATE`.
7. Проверь на локальном Postgres (`docker compose -f infra/docker-compose.yml up -d`):
   - миграция применяется на пустой базе;
   - миграция применяется на базе с данными предыдущей версии;
   - тесты сервиса проходят.
8. В описании PR укажи, совместима ли миграция с предыдущей версией кода и почему.

Для таблиц денег в `engine` дополнительно: не меняй и не удаляй существующие проводки ledger. История проводок только дополняется.
